# git

Everything git lives here, next to its config: the file mechanics, the
signing, the aliases, and the why behind the chosen defaults.

## The five files

| File | Role |
|---|---|
| `config` | the versioned config, portable as-is to any machine. Holds the DEFAULT identity (GitHub) and the two conditions that switch it |
| `config.gitlab` | the GitLab identity, versioned too. Pulled in only by those conditions |
| `config.local` | the **machine-local** part: `gpg.ssh.allowedSignersFile` (always), plus `user.signingkey` and `commit.gpgsign` when a key is present, and `gpg.ssh.program` on macOS + Homebrew. Generated by `./run install gitsign`, gitignored, silently included when missing |
| `allowed_signers` | the signers accepted by `git log --show-signature` (ssh format). **Maintained by `./run install gitsign`**, append-only: one line per identity, all naming the same signing key |
| `ignore` | global excludes, OS and editor junk only; project-specific patterns belong in each repo's `.gitignore` |

The config / config.local split is what keeps the repo portable: the key
and the `ssh-keygen` path differ per machine, so they have no business in a
versioned file.

`user.name` and `user.email` sit in `config`, versioned on purpose: one
person, several machines, one edit.

> [!IMPORTANT]
> Changing `user.email` does **not** break local verification: `git
> verify-commit` matches a signature by its **key**, never by the author's
> address (measured — `allowed_signers` says how). What it does break is the
> **forge** side: GitHub and GitLab attribute a commit, and mark it *Verified*,
> by the address it carries. An address they do not know leaves the commit
> unattributed and unverified there, whatever the signature proves here.

## Two forges, one machine

The identity is not global any more. `config` carries the GitHub address as
the **default**, and `config.gitlab` overrides it under two conditions:

| Condition | Matches on | Covers |
|---|---|---|
| `gitdir:~/lab/gitlab/` | the **path** | a `git init` there, before any remote exists |
| `hasconfig:remote.*.url:git@gitlab.com:**/**` | the **remote URL** | a GitLab repo cloned anywhere at all |

The second is the important one: **`~/lab/gitlab` is a tidiness habit, not a
requirement.** Clone a GitLab repo into `/tmp`, onto the Desktop, into a
client folder — as soon as `origin` points at `gitlab.com`, the GitLab
identity applies. `ghc` and `glc` only save typing.

The default has to stay a real address: a repository matching neither
condition still needs an email, or git refuses to commit.

> [!WARNING]
> Two traps, both measured:
>
> - A repo **outside** `~/lab/gitlab` with **no remote yet**. `git init`,
>   commit, and those commits carry the GitHub address. Add the remote before
>   the first commit, or repair with `git commit --amend --reset-author`.
> - The reverse: a **GitHub** repo placed **inside** `~/lab/gitlab` gets the
>   GitLab identity. `gitdir` matched, and nothing contradicts it — the URL
>   condition only ever *adds* GitLab, it never takes it back. The directory
>   is a convenience, but it is not neutral: keep a forge's repos out of the
>   other's folder, or check with `git config user.email` before committing.

Check which identity a repository actually uses, from inside it:

```sh
git config user.email     # the answer git will really use here
```

`hasconfig` requires git ≥ 2.36. And git expands no variable inside a
condition, so `~/lab/gitlab` is written out: if `$REPOS` ever moves, that line
moves with it.

## Signing

Commits are ssh-signed (`gpg.format = ssh`) with a FIDO2 `sk-ssh-ed25519`
key (YubiKey). The `ssh-keygen` able to sign with these keys differs per
OS: Homebrew's on macOS (Apple's build cannot), the system one on Fedora
(native FIDO2). That is why `gpg.ssh.program` lives in `config.local`,
written by the gitsign step from what the machine actually has.

### Creating the keys (YubiKey)

<details>
<summary>The two credentials, flag by flag</summary>

Three distinct FIDO2 credentials live on the one YubiKey, one per job, so
revoking or rotating one never touches the others. One physical key is
enough: `-O application=…` namespaces each credential:

```sh
# 1. Commit signing, no touch required: a deliberate, accepted trade.
#    Given up: physical presence per signature. Accepted risk: malware on
#    an unlocked machine with the key plugged in can sign silently, and
#    verification can never tell (allowed_signers has no touch field).
#    Kept because signing fires on every commit and the AUTH key below
#    still demands a PIN: the stronger right keeps the stronger guard.
/opt/homebrew/opt/openssh/bin/ssh-keygen -t ed25519-sk -O resident \
  -O no-touch-required -O application=ssh:signing \
  -C "signing-yubikey" -f ~/.ssh/id_signing_sk

# 2. GitHub authentication, PIN required: pushing is a more powerful
#    right than signing, it costs a PIN.
/opt/homebrew/opt/openssh/bin/ssh-keygen -t ed25519-sk -O resident \
  -O verify-required -O application=ssh:github \
  -C "github-yubikey" -f ~/.ssh/github_sk

# 3. GitLab authentication, PIN required. Its OWN credential rather than a
#    second use of #2: losing or revoking access to one forge must never
#    cost access to the other. Signing needs no equivalent -- a signature
#    is not an access, so the one signing key above serves both forges.
/opt/homebrew/opt/openssh/bin/ssh-keygen -t ed25519-sk -O resident \
  -O verify-required -O application=ssh:gitlab \
  -C "gitlab-yubikey" -f ~/.ssh/gitlab_sk
```

Flag by flag: the full Homebrew path because Apple's `ssh-keygen` cannot
create `sk-*` keys; `-O resident` stores the credential on the YubiKey
itself, so on a new machine `ssh-keygen -K` regenerates the key handles
with no file to transfer; `-O application=ssh:…` namespaces each
credential so both coexist on one key.

</details>

Wiring, forge by forge. On **GitHub**: upload `id_signing_sk.pub` as a
**signing key** and `github_sk.pub` as an **authentication key** (two separate
dropdowns).

On **GitLab**: upload `gitlab_sk.pub` and, again, `id_signing_sk.pub` — the
same signing key as GitHub, which is the whole point. GitLab has **one**
dropdown, *Usage type*: `Authentication` for the first, `Signing` (or
`Authentication & Signing`) for the second. A key left on `Authentication`
will not make signatures verify. And the address in `config.gitlab` must be a
**verified** email on the account, or every commit shows as unverified
whatever the signature proves.

Then point ssh at each auth key:

```sshconfig
# ~/.ssh/config
# First, globally: brew's openssh (installed for FIDO2) shadows Apple's
# ssh and knows no UseKeychain, so IgnoreUnknown must precede any use.
IgnoreUnknown UseKeychain

Host github.com
  IdentityFile ~/.ssh/github_sk
  IdentitiesOnly yes
  # macOS ssh-agent has no security-key support and refuses to sign
  # ("agent refused operation"): bypass it, talk to the authenticator.
  AddKeysToAgent no
  IdentityAgent none

Host gitlab.com
  IdentityFile ~/.ssh/gitlab_sk
  IdentitiesOnly yes
  AddKeysToAgent no
  IdentityAgent none
```

Neither `github_sk` nor `gitlab_sk` is a name ssh tries on its own: without
these two blocks the connection falls back to the default key names and is
refused.

The signing side needs no manual wiring: `~/.ssh/id_signing_sk.pub` is
exactly the file the gitsign step looks for, and `./run install gitsign`
writes `user.signingkey` and `commit.gpgsign` into `config.local` on its
own.

### Checking that it works

Four things can be wrong independently — identity, access, signature, and
whether `allowed_signers` agrees with the key on disk. Test them in that
order, because each one explains the next.

**1. The identity, per location.** This is pure config, no hardware:

```sh
cd ~/lab/github/anything  && git config user.email   # …@users.noreply.github.com
cd ~/lab/gitlab/anything  && git config user.email   # …@users.noreply.gitlab.com
cd /tmp && git init -q gl-test && cd gl-test \
  && git remote add origin git@gitlab.com:racongiu/x.git \
  && git config user.email                           # gitlab, OUTSIDE ~/lab
```

**2. The access, one run per forge:**

```sh
ssh -T git@github.com    # "Hi Raf7c! You've successfully authenticated…"
ssh -T git@gitlab.com    # "Welcome to GitLab, @racongiu!"
```

Two runs, one per forge. They prove the right key reached the right account —
`github_sk` and `gitlab_sk` are separate credentials on the one YubiKey, so a
success on one says nothing about the other.

**3. The signature, end to end**, in a throwaway repo:

```sh
cd /tmp && rm -rf sigtest && mkdir sigtest && cd sigtest && git init -q .
git commit -q --allow-empty -m test
git verify-commit HEAD           # exit 0
git log --show-signature -1      # Good "git" signature with …
```

A signature made by a key absent from `allowed_signers` fails here while the
forge shows it as verified: that is the confusing case this step rules out.

**4. `allowed_signers` agrees with the keys on disk.** Transcription is the
one thing the append command exists to avoid; verify it worked:

```sh
grep -cF "$(cut -d' ' -f2 ~/.ssh/id_signing_sk.pub)" ~/.config/git/allowed_signers
```

Two: one principal per identity, GitHub and GitLab, for the one signing key.
The count is what matters here, not which name git will print — that is the
first matching line, in file order.

A failure at step 3 is almost always one of three things: no
`allowedSignersFile` (regenerate `config.local` with `./run install gitsign`),
**the key** absent from `allowed_signers` — the address is not what is
matched — or a commit dated before the `valid-after` of the line that does
match (see below).

### Rotating the signing key

`allowed_signers` is time-aware: git hands each commit's date to
`ssh-keygen -Y verify`, which checks it against the `valid-after` /
`valid-before` window of every line. Rotating therefore means keeping
**both** keys, each with its own window:

```text
me@example  namespaces="git",valid-before="20260804"  sk-ssh-ed25519@openssh.com AAAA…old
me@example  namespaces="git",valid-after="20260804"   sk-ssh-ed25519@openssh.com AAAA…new
```

Every commit is then verified by the key that was valid at its date. Drop
the old line and its commits stop verifying: the signature is still in
the object, but nothing can confirm it any more. Same on GitHub: unregister
the old public key and those commits fall back to Unverified.

> [!NOTE]
> That is exactly what happened here, and it is a **deliberate** choice, not
> an oversight. The July 2026 key was retired without a `valid-before` line,
> so the commits it signed between 2026-07-27 and 2026-08-04 — about twenty
> here, about fifteen in the school repo — no longer verify, locally or on
> GitHub once the old public key
> is unregistered. Only one person ever wrote them, the current key is the
> only one in use, and carrying a retired credential forward to rescue eight
> days of history was judged not worth it. A branch ruleset requiring signed
> commits does not change this: it applies to what is pushed from now on, not
> retroactively to history already on the branch.

## Aliases

None here, on purpose: they are **shell** aliases (`gst`, not `git st`)
and live in `shell/aliases.sh`, see
[docs/usage.md](../../docs/usage.md). Accepted cost: they exist only
in interactive shells; scripts and tools call plain git.

## Notable defaults

| Setting | Why |
|---|---|
| `diff.algorithm = histogram` | better hunks than myers when blocks move |
| `merge.conflictStyle = zdiff3` | the conflict also shows the common base, not just both sides |
| `rerere` (+ autoupdate) | a conflict resolved once is replayed on later rebases |
| `pull.rebase` + `rebase.autoStash/autoSquash/updateRefs` | linear history; `updateRefs` moves stacked branches along |
| `push.autoSetupRemote` | first push without `-u` |
| `push.followTags` + `fetch.prune`/`pruneTags` | tags and refs in sync both ways |
| `transfer.fsckObjects` | object integrity checked on every transfer |
| `commit.verbose` | the diff below the commit message, in the editor |
| `help.autocorrect = prompt` | suggests the fix, never runs it on its own |
| `branch.sort` / `tag.sort` | recent branches first, version-sorted tags |
| `merge/diff.tool = editor` | follows `$EDITOR`, so you change the editor once and diff and merge follow; `trustExitCode = false`: an editor exit code says nothing about a merge |
